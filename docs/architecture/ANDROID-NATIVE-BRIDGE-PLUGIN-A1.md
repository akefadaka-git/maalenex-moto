## 1. Purpose and stage boundary

This document defines the proposed native messaging boundary between the MaaleNex React frontend and the existing Android native shell. It also defines the plugin registration contract, permission and authorization rules, threat model, abuse-case tests, and CI evidence contract.

A1 freezes the design baseline for a separately authorized A3 implementation. It does not assert that the bridge or any native plugin exists.

### 1.1 Existing verified baseline

At the baseline commit:

- Android launches `com.maalenex.moto/.MainActivity`.
- `MainActivity` creates an AndroidX WebView and serves packaged frontend assets through `WebViewAssetLoader`.
- The app entry URL is `https://appassets.androidplatform.net/assets/www/index.html`.
- AndroidX WebKit `1.12.1` is already declared.
- JavaScript and DOM storage are enabled; file access, content access, and mixed content are disabled.
- The frontend is React/TypeScript/Vite.
- No Capacitor runtime, JS-to-native bridge, native capability registry, or native plugin is configured.
- Emulator run #43592760041 passed the native startup and WebView/DOM-root smoke gates. The CI script did not retain the exact parsed JavaScript probe JSON as a visible log line; A3 must correct that evidence gap.

### 1.2 A1 non-goals

A1 does not implement:
- `WebMessageListener` registration or JavaScript bridge objects;
- native plugin classes or plugin dependencies;
- Android manifest permissions;
- authentication/session integration;
- production secrets, signing keys, or real user data;
- backend API changes, commercial operations, deployment, release, or merge.

No unrestricted `addJavascriptInterface` bridge is permitted.

## 2. Architecture decision

### ADR-A1-01 — Retain native WebView; use AndroidX WebMessageListener

**Decision:** Retain the existing native Android Activity and packaged WebView. When A3 is separately authorized, implement a small, versioned JSON bridge using AndroidX WebKit `WebViewCompat.addWebMessageListener`.

**Rationale:**
1. The current native shell and packaged frontend already boot and render.
2. The project can expose narrowly scoped capabilities without introducing a general-purpose cross-platform runtime.
3. The bridge can enforce an exact allowed-origin rule and inspect the sender origin and main-frame flag.
4. A capability registry keeps Android APIs inaccessible unless a specific, reviewed capability is registered.

**Rejected for v1:**
- Capacitor adoption solely to obtain a bridge; reconsider only if a future cross-platform requirement justifies the runtime.
- `addJavascriptInterface`; its interface is exposed to frames and has a materially broader attack surface.
- Arbitrary reflection, class names, method names, intents, filesystem paths, or permission requests supplied by JavaScript.

### 2.1 Trust-boundary diagram

```text
React / TypeScript feature code
        |
        | typed request; JSON only
        v
Frontend Bridge Client
        |
        | window.postMessage to named listener
        v
AndroidX WebMessageListener
        |
        | exact origin + main-frame + schema + size + rate checks
        v
Native Bridge Dispatcher
        |
        | capability allowlist + authorization + permission checks
        v
Native Capability Registry
        |
        +--> approved Android capability modules
        |
        +--> structured response / sanitized error
        v
Frontend Bridge Client
```

The bridge is a privileged boundary. Frontend code is not trusted merely because it is bundled locally: XSS, compromised dependencies, unsafe HTML rendering, or a future content-loading mistake could execute attacker-controlled JavaScript in the trusted origin.

## 3. Bridge protocol v1

### 3.1 Transport and namespace

- Native listener name: `maalenexNative`.
- Android transport: `WebViewCompat.addWebMessageListener`.
- Frontend transport: `window.maalenexNative.postMessage(JSON.stringify(request))`.
- Responses/events: delivered through the listener's message port / reply channel defined by the Android implementation.
- Serialization: UTF-8 JSON only. No arbitrary JavaScript objects, functions, binary blobs, or Java/Kotlin object serialization.
- Protocol version: integer `1`.
- Request IDs: UUID v4 strings generated by the frontend.
- Maximum serialized request: **64 KiB**.
- Maximum in-flight requests per WebView: **32**.
- Default request timeout: **15 seconds**; capability-specific limits may be shorter.
- Unknown protocol versions, capabilities, actions, fields, or message types are rejected.

The bridge client must fail closed if the WebMessageListener feature is unavailable in the installed Android System WebView. The app may continue to run as a web-backed app with native capabilities marked unavailable; it must not silently fall back to `addJavascriptInterface`.

### 3.2 Request envelope

```typescript
export type BridgeRequestV1<TPayload = unknown> = {
  protocol: 1;
  type: "request";
  requestId: string; // UUID v4
  capability: string; // e.g. "device.info"
  action: string;     // e.g. "get"
  issuedAt: number;   // Unix epoch milliseconds; diagnostic only
  payload: TPayload;
};
```

Example:

```json
{
  "protocol": 1,
  "type": "request",
  "requestId": "3e0c5b32-2e84-4f91-9b85-47c17d98a130",
  "capability": "device.info",
  "action": "get",
  "issuedAt": 1794664800000,
  "payload": { "fields": ["platform", "appVersion"] }
}
```

The timestamp is not an authentication factor and must not be used as proof of user identity or request freshness.

### 3.3 Response envelope

```typescript
export type BridgeSuccessV1<TData = unknown> = {
  protocol: 1;
  type: "response";
  requestId: string;
  ok: true;
  data: TData;
};

export type BridgeFailureV1 = {
  protocol: 1;
  type: "response";
  requestId: string;
  ok: false;
  error: {
    code: BridgeErrorCode;
    message: string; // safe, non-sensitive, user-displayable summary
    retryable: boolean;
  };
};

export type BridgeErrorCode =
  | "INVALID_MESSAGE"
  | "UNSUPPORTED_PROTOCOL"
  | "ORIGIN_DENIED"
  | "FRAME_DENIED"
  | "UNKNOWN_CAPABILITY"
  | "UNKNOWN_ACTION"
  | "PAYLOAD_INVALID"
  | "PAYLOAD_TOO_LARGE"
  | "RATE_LIMITED"
  | "REQUEST_EXPIRED"
  | "REQUEST_CANCELLED"
  | "PERMISSION_DENIED"
  | "AUTHENTICATION_REQUIRED"
  | "NOT_AUTHORIZED"
  | "CAPABILITY_UNAVAILABLE"
  | "NATIVE_FAILURE"
  | "INTERNAL_ERROR";
```

Never return stack traces, filesystem paths, tokens, keystore aliases, raw Android exception messages, or internal authorization details to JavaScript.

### 3.4 Events

Events are optional and capability-specific. An event envelope is:

```typescript
export type BridgeEventV1<TData = unknown> = {
  protocol: 1;
  type: "event";
  eventId: string;
  capability: string;
  event: string;
  emittedAt: number;
  data: TData;
};
```

The frontend must subscribe only to documented event names. Events must not contain credentials or unnecessary personal data. Event subscriptions are removed when the WebView or owning feature is disposed.

### 3.5 Frontend TypeScript API

The public frontend surface is deliberately narrow:

```typescript
export interface NativeBridge {
  readonly availability: "available" | "unavailable";
  request<TRequest, TResponse>(
    capability: string,
    action: string,
    payload: TRequest,
    options?: { timeoutMs?: number; signal?: AbortSignal }
  ): Promise<TResponse>;
  on<TEvent>(
    capability: string,
    event: string,
    listener: (event: TEvent) => void
  ): () => void;
}

declare global {
  interface Window {
    maalenexNative?: {
      postMessage(message: string): void;
      addEventListener(
        type: "message",
        listener: (event: MessageEvent<string>) => void
      ): void;
      removeEventListener(
        type: "message",
        listener: (event: MessageEvent<string>) => void
      ): void;
    };
  }
}
```

Implementation requirements:
- The application feature layer imports a typed wrapper; feature code does not handcraft arbitrary bridge envelopes.
- Capability/action strings are generated from a closed frontend contract, not user input.
- Validate every response against a runtime schema before returning it to feature code.
- Reject duplicate/unknown response IDs and ignore late responses after timeout/cancellation.
- Do not expose a generic `invoke(className, methodName, args)` API.
- No secret or bearer token is passed as bridge payload merely to authorize a native operation.

## 4. Android listener and exact origin/frame enforcement

### 4.1 Allowed origin

The only allowed origin in v1 is:

- Scheme: `https`
- Host: `appassets.androidplatform.net`
- Port: default HTTPS port only (no explicit non-default port)
- User information: absent
- Listener allowed-origin rule: `https://appassets.androidplatform.net`

Origin matching does not include a path. Therefore the listener's allowed-origin rule must be paired with navigation policy, frame policy, and message-level checks.

### 4.2 Required listener checks

The A3 Android listener must perform these checks in order, before dispatch:

1. Check `WebViewFeature.WEB_MESSAGE_LISTENER` using `WebViewFeature.isFeatureSupported`. If unavailable, do not register an alternate insecure bridge.
2. Register the listener before the first `loadUrl`.
3. Configure the listener with only the exact HTTPS asset origin above; do not use wildcard origins.
4. On every message, require `isMainFrame == true`.
5. Require `sourceOrigin.scheme == "https"`, host exactly `appassets.androidplatform.net`, and default HTTPS port; reject user-info and any unexpected origin.
6. Reject empty messages and messages over 64 KiB before JSON parsing.
7. Parse JSON into a strict envelope; reject unknown protocol version, message type, duplicate/unknown fields where strict decoding supports it, malformed UUIDs, and invalid payload schemas.
8. Apply rate and in-flight limits before dispatch.
9. Dispatch only through the capability registry.
10. Return a correlated, sanitized response; do not leak native exception detail.

The callback's `sourceOrigin` and `isMainFrame` are authoritative inputs to the check. Do not trust origin, frame, capability, user, or permission claims inside the JSON payload.

### 4.3 Navigation and content policy

Before enabling the bridge, A3 must harden the current navigation rule. The current implementation checks host and path prefix, but does not explicitly check scheme, port, or user-info.

Required navigation policy:
- Main-frame navigation is allowed only to HTTPS `appassets.androidplatform.net`, default port, no user-info, and the packaged `/assets/` path.
- All other main-frame navigations are blocked in the WebView. External navigation, if later required, must use a separate explicit user-confirmed native flow.
- Do not load arbitrary remote HTML, scripts, frames, or executable content into the trusted WebView.
- Add a Content Security Policy appropriate to the built frontend: scripts from the packaged origin only; `object-src 'none'`; `base-uri 'self'`; `frame-src 'none'` unless a reviewed use case requires otherwise. API `connect-src` entries must be explicit and limited to approved backend origins.
- Do not enable file URL access, universal file URL access, mixed content, or unrestricted content access.
- A subframe must never receive native capability access.

A navigation check based only on `host` and `path.startsWith("/assets/")` is insufficient for bridge activation.

### 4.4 Lifecycle and teardown

- Register the listener before loading the trusted entry URL.
- Bind bridge state to the current WebView instance and page lifecycle.
- On page navigation, renderer loss, Activity destruction, or WebView replacement: reject new requests, cancel pending requests, remove event subscriptions, clear pending callbacks, and remove the listener where supported.
- A newly loaded document must establish a new bridge-ready handshake; prior page state is not reusable.
- Never retain an Activity, WebView, or JavaScript reply proxy in a process-wide singleton.

## 5. Capability registry and plugin lifecycle

### 5.1 Capability descriptor

Each native module must provide a static descriptor reviewed at build time:

```kotlin
data class CapabilityDescriptor(
    val id: String,
    val version: Int,
    val supportedActions: Set<String>,
    val requiredPermissions: Set<String>,
    val requiresRecentAuthentication: Boolean,
    val minimumAppVersion: Int
)
```

The registry must reject duplicate IDs, unsupported versions, undeclared actions, and modules that request permissions outside their approved descriptor. No runtime class loading or reflection-based plugin discovery is allowed.

### 5.2 Lifecycle state machine

```text
UNINITIALIZED
    |
    v
VALIDATING -----> FAILED
    |
    v
REGISTERED
    |
    v
READY <-------> SUSPENDED
    |
    v
DISPOSING
    |
    v
DISPOSED
```

Rules:
- **UNINITIALIZED:** module has not been inspected.
- **VALIDATING:** validate descriptor, version, dependencies, permission declarations and platform support.
- **REGISTERED:** known to the registry but not callable.
- **READY:** all non-user permissions and prerequisites are satisfied; individual actions may still require runtime authorization.
- **SUSPENDED:** app is backgrounded, permission is revoked, authentication expires, or platform prerequisites disappear.
- **FAILED:** initialization or invariant validation failed; capability remains unavailable.
- **DISPOSING/DISPOSED:** cancel work, unregister callbacks, release resources and reject new calls.

A capability must not transition to READY merely because it was registered. Permission and authorization checks occur for each sensitive operation, not only at initialization.

### 5.3 Dispatch contract

Each action handler receives:
- validated request ID and payload;
- caller origin/frame context already verified by the bridge;
- current app/user session state from a trusted native source;
- permission state from Android;
- an operation-scoped cancellation signal.

Each handler returns a typed result or a typed error. Handlers must not receive unrestricted Activity access unless strictly necessary; UI-bound operations must use a lifecycle-safe Activity provider and fail if no valid foreground Activity exists.

### 5.4 Initial plugin catalogue

No plugin is implemented by A1. The following is the approved candidate catalogue for A3 planning:

| Capability ID | Initial actions | Priority | v1 boundary |
|---|---|---:|---|
| `device.info` | `get` | P1 | Allowlisted non-sensitive fields only |
| `auth.biometric` | `authenticate` | P0 | Native biometric prompt; no biometric data exposed |
| `storage.secure` | `get`, `set`, `delete` | P0 | App-scoped encrypted key/value data only |
| `notifications.local` | `requestPermission`, `schedule`, `cancel` | P1 | Local notifications only; no silent privilege escalation |
| `media.camera` | `capture` | P1 | User-initiated capture and scoped output |
| `location.foreground` | `getCurrent`, `startUpdates`, `stopUpdates` | P1 | Foreground, consent-based location only |
| `files.document` | `pick` | P2 | Android system picker / SAF; user-selected files only |

Explicit exclusions from v1:
- background location;
- broad filesystem enumeration or arbitrary file paths;
- contacts, call logs, SMS, microphone recording, accessibility service control;
- device administrator/device-owner privileges;
- arbitrary intents, shell commands, package installation, or app launching;
- unrestricted clipboard access;
- biometric templates or raw authentication secrets.

## 6. Permission and authorization matrix

Permission and authorization are distinct:
- **Android permission** is the OS grant, requested only when a user invokes a feature that needs it.
- **App authorization** is the current authenticated user's permission to perform that operation.
- **Recent authentication** is a separate native confirmation gate for high-impact local operations.

| Capability/action | Android permission / OS API | App authorization | Additional gate |
|---|---|---|---|
| `device.info.get` | None for allowlisted basic app/device fields | Authenticated app session where data is account-linked | Data minimization |
| `auth.biometric.authenticate` | BiometricPrompt capability; no runtime permission | User must be in an eligible app flow | OS biometric/PIN credential prompt |
| `storage.secure.get/set/delete` | None; Android Keystore | Authenticated user and per-key access policy | Recent biometric/device credential for sensitive keys |
| `notifications.local.requestPermission` | Android 13+ `POST_NOTIFICATIONS`; older versions use OS notification settings | User-initiated opt-in | Explain purpose before OS prompt |
| `notifications.local.schedule/cancel` | Notification permission and channel availability | Only notifications belonging to the current app account/session | Validate schedule and content |
| `media.camera.capture` | `CAMERA` runtime permission if using direct camera API; system capture contract may provide a narrower flow | User-initiated capture | Visible camera UI; no background capture |
| `location.foreground.getCurrent/startUpdates` | `ACCESS_COARSE_LOCATION` and/or `ACCESS_FINE_LOCATION` as justified | Explicit feature-level consent and account authorization | Foreground-only; explain precision |
| `files.document.pick` | Android Photo Picker or Storage Access Framework URI grant; avoid broad storage permission | User-selected document must be valid for the current workflow | MIME/size validation; persist URI grant only if needed |

Rules:
1. Do not request all permissions at first launch.
2. Request permission only at the point of use, after explaining the feature.
3. If permission is denied, return `PERMISSION_DENIED`; do not loop prompts or degrade into a broader permission.
4. If permission is permanently denied, guide the user to system settings only after an explicit user action.
5. Permission revocation immediately suspends affected capability operations.
6. Backend authorization must still be enforced server-side for account, booking, payment, identity, and other protected business operations. A local bridge check is not a substitute for backend authorization.
7. No payment, wallet signing, account recovery, identity proofing, or financial transaction signing capability is included in this initial catalogue.

## 7. Security threat model

### 7.1 Assets

- authenticated app session and account identifiers;
- Keystore-protected encryption keys and secure local data;
- biometric prompt result (never biometric templates);
- location and user-selected documents;
- notification content;
- integrity of native operations and bridge responses;
- availability and lifecycle state of the WebView and native modules.

### 7.2 Trust assumptions

- Bundled frontend code can still be compromised by XSS or a malicious dependency.
- The app asset origin is trusted only when navigation and content-loading policy remain constrained.
- A same-origin script can invoke the bridge; therefore XSS within the trusted origin is a privileged compromise.
- Android permission grants do not prove the user is authorized for a business operation.
- CI emulator success does not prove physical-device, OEM, rooted-device, or production security.

### 7.3 Threats and mitigations

| Threat | Example / impact | Required mitigation |
|---|---|---|
| T1 Origin spoofing | External page attempts to call the bridge | Exact WebMessageListener origin rule and runtime source-origin check |
| T2 Subframe abuse | Embedded iframe sends privileged requests | Require `isMainFrame`; block frames by CSP |
| T3 XSS / dependency compromise | Malicious same-origin script invokes native capabilities | CSP, dependency review, safe rendering, capability minimization, user confirmation for sensitive actions |
| T4 Navigation escape | WebView navigates to remote page while retaining bridge | Exact HTTPS host/port/user-info/path policy; reject external main-frame navigation |
| T5 Message injection | Malformed or oversized JSON exhausts parser/resources | 64 KiB limit, strict schema, bounded parser, rate limits |
| T6 Replay / duplicate action | Repeated payment-like or destructive operation | Idempotency keys for state-changing actions, duplicate request tracking, backend idempotency; no financial plugin in v1 |
| T7 Confused deputy | Frontend asks native module to perform action for another account | Native session binding, per-action authorization, server-side authorization |
| T8 Permission abuse | Permission requested without feature context | Just-in-time requests, consent, narrow scope, no permission escalation |
| T9 Sensitive-data leakage | Tokens or private data appear in logcat or JS errors | Redacted structured logging; never log payloads or secrets |
| T10 Lifecycle race | Delayed callback reaches destroyed Activity/WebView | Lifecycle-bound cancellation, generation IDs, stale callback rejection |
| T11 Plugin privilege escalation | Module registers undeclared action or permission | Static descriptor allowlist, duplicate rejection, build-time manifest audit |
| T12 Denial of service | Request flood or infinite native work | In-flight cap, rate limit, timeout, cancellation, bounded queues |
| T13 Renderer compromise | WebView renderer crashes or is terminated | Fail closed, clear pending operations, recreate WebView and bridge handshake |
| T14 Local device compromise | Rooted or instrumented device tampers with process | Treat local checks as defense-in-depth; backend risk controls; do not claim root detection is definitive |

### 7.4 Logging and privacy

- Log event type, request ID, capability/action identifier, outcome code, duration, and a non-sensitive correlation identifier.
- Never log raw request payloads, response data, access tokens, document contents, precise location, biometric data, or secure-storage values.
- Log security rejections with reason codes, not attacker-controlled message bodies.
- Do not expose internal stack traces to the frontend.
- CI probe output is a separate, synthetic diagnostic payload and must not include page text or user data.

A3 implementation is not complete until automated tests cover at least these cases:

| Test ID | Abuse case | Expected result |
|---|---|---|
| BR-001 | Exact trusted HTTPS origin, main frame, valid request | Request reaches only the declared handler |
| BR-002 | Same host over HTTP | Rejected; no dispatch |
| BR-003 | Trusted host with non-default port | Rejected |
| BR-004 | Trusted host with user-info component | Rejected |
| BR-005 | Lookalike host such as `appassets.androidplatform.net.attacker.invalid` | Rejected |
| BR-006 | External origin | Rejected by listener allowlist and runtime check |
| BR-007 | Trusted-origin iframe | Rejected because `isMainFrame=false` |
| BR-008 | Navigation to external main-frame URL | Blocked |

| BR-010 | Malformed JSON / wrong top-level type | `INVALID_MESSAGE`; no crash |

Tests must include unit tests for protocol/schema/registry, Android instrumentation tests for WebView origin/frame behavior, and emulator end-to-end tests for bridge handshake and negative cases. A test that only calls a Kotlin handler directly is not evidence of origin/frame enforcement.

## 9. CI WebView JavaScript probe evidence contract

The current smoke script checks for fragments in logcat but does not retain the exact decoded JSON probe payload in the successful run output. A3 must make the payload auditable.

### 9.1 Probe payload schema

The JavaScript probe must return a JSON object with only non-sensitive diagnostic fields:

```typescript
export interface WebViewProbeV1 {
  schemaVersion: 1;
  readyState: "loading" | "interactive" | "complete";
  title: string;
  rootPresent: boolean;
  rootTextLength: number;
}
```

Do not log `innerText`, HTML, tokens, user data, network response bodies, or arbitrary page state.

### 9.2 Native log preservation

The `evaluateJavascript` callback returns a JSON-encoded JavaScript string when the script returns `JSON.stringify(...)`. The Android callback must decode that returned string, parse it as JSON, validate its schema, and log one compact single-line record:

```text
WEBVIEW_JS_PROBE_JSON {"schemaVersion":1,"readyState":"complete","title":"MaaleNex","rootPresent":true,"rootTextLength":42}
```

The example values are illustrative; CI must assert the actual runtime payload, not compare against a hardcoded title or text length.

### 9.3 CI assertions

The emulator smoke test must:
1. Clear or timestamp logcat before app launch so stale lines cannot satisfy the gate.
2. Wait for the current process's `WEBVIEW_PAGE_FINISHED` and `WEBVIEW_JS_PROBE_JSON`.
3. Extract exactly one valid probe JSON line for the current run; fail on missing or malformed JSON.
4. Parse the JSON with a real JSON parser, not grep-only substring matching.
5. Assert `schemaVersion == 1`.
6. Assert `readyState == "complete"`.
7. Assert `rootPresent is true`.
8. Assert `rootTextLength` is an integer greater than zero.
9. Print the exact decoded JSON line into the GitHub Actions job log and write the same line into `$GITHUB_STEP_SUMMARY`.
10. Upload the probe text artifact with bounded retention, even on failure, where feasible.
11. Assert no `WEBVIEW_MAIN_FRAME_ERROR`, `FATAL EXCEPTION`, or WebView renderer crash was observed during the smoke window.
12. Print explicit PASS/FAIL markers for each gate.

The CI output must preserve the exact payload returned by the emulator. Do not reconstruct a synthetic JSON object from grep matches and present it as runtime evidence.

### 9.4 Probe acceptance example

```text
WEBVIEW_PAGE_FINISHED url=https://appassets.androidplatform.net/assets/www/index.html
WEBVIEW_JS_PROBE_JSON {"schemaVersion":1,"readyState":"complete","title":"MaaleNex","rootPresent":true,"rootTextLength":42}
PASS: WebView probe JSON parsed
PASS: readyState=complete
PASS: rootPresent=true
PASS: rootTextLength>0
```

## 10. A3 implementation sequence and acceptance gates

A3 must be separately authorized and should proceed in this order:

1. **A3.1 — CI probe evidence correction:** decode, log, preserve and parse the exact WebView JSON payload; verify `readyState=complete`.
2. **A3.2 — Navigation/content hardening:** enforce exact scheme/host/port/user-info/path rules and CSP before bridge registration.
3. **A3.3 — Protocol implementation:** strict request/response envelopes, schema validation, correlation, timeouts, cancellation and limits.
4. **A3.4 — Android listener:** feature check, exact origin allowlist, main-frame enforcement and lifecycle-safe registration.
5. **A3.5 — Capability registry:** static descriptors, duplicate rejection, lifecycle and dispatch.
6. **A3.6 — Initial P0 capabilities:** biometric authentication and app-scoped secure storage, only after separate permission/security review.
7. **A3.7 — Negative security tests:** origin/frame, malformed messages, authorization, rate, lifecycle and log-leak cases.
8. **A3.8 — Independent security review:** review implementation and test evidence before declaring bridge ready.

A gate cannot be skipped because a later functional test passes. If origin/frame or authorization enforcement fails, bridge activation is blocked.

### 10.1 A3 exit criteria

- All protocol and registry unit tests pass.
- Android instrumentation tests prove exact origin and main-frame enforcement.
- Emulator smoke test preserves and parses the actual probe JSON with `readyState=complete`.
- All required abuse tests pass.
- No unapproved Android permissions or bridge methods exist.
- No sensitive values are logged or returned to JavaScript.
- Independent security review has no unresolved critical/high findings.
- Physical-device compatibility is tested on at least one supported Android device before production consideration.
- Production activation, merge, release and deployment remain separate owner decisions.

## 11. A1 freeze record

### Frozen decisions

1. Retain the direct native Android WebView architecture for v1.
2. Use AndroidX `WebMessageListener`; do not use `addJavascriptInterface`.
3. Allow only the exact HTTPS asset origin `https://appassets.androidplatform.net`.
4. Require main-frame messages and exact runtime sender-origin checks.
5. Use protocol v1 with typed JSON request/response/event envelopes.
6. Expose only statically registered, explicitly authorized capabilities.
7. Keep plugin permissions just-in-time and feature-specific.
8. Exclude background location, broad storage, financial signing, arbitrary intents and unrestricted device APIs from v1.
9. Preserve the actual WebView probe JSON in CI and assert `readyState=complete`.
10. Keep bridge/plugin implementation and production activation outside A1.

### Freeze status and change control

This document is the A1 design baseline prepared under the requested A1 scope. It is frozen for implementation planning; it is not a claim that the Owner has separately approved production activation or every future plugin.

Any change to transport, trusted origin, frame policy, permission scope, protocol compatibility, or capability exposure requires a documented architecture decision and security-impact review before implementation. A material security contradiction or platform incompatibility may reopen the affected decision; unrelated changes do not reopen this baseline.
